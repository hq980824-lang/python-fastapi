## 三、核心设计难题（好友功能的精髓，没标准答案，先想清楚）

### 难题 A：一条记录 vs 两条记录（地基决策，影响全部）

A 和 B 成为好友，数据库怎么存？

- **方案：存 1 条** `(user_id=A, friend_id=B, status=accepted)`
  - 优点：数据不冗余，删除/状态管理简单（一段关系一条记录）。
  - 缺点：查「我的好友」要双向查（既查 user_id=我、又查 friend_id=我），用 `or`_。单向属性（备注）不好存。
- **方案：存 2 条** `(A,B)` 和 `(B,A)`
  - 优点：查好友只查 user_id=我（单向，简单）；单向属性（备注/分组）天然各存各的。
  - 缺点：数据冗余，状态要同步两条，删除要删两条。

**建议**：阶段一（核心关系）用 **1 条记录**（关系语义清晰、防重复靠联合唯一约束方便）。等做到备注/分组（单向属性）时再权衡——这正是难题 B。

> **业界真实方案（QQ/微信这类）：两条记录（双向冗余存储）。**
> A、B 成为好友存两条 `(owner=A, friend=B)` 和 `(owner=B, friend=A)`，每条 = 「我视角的这个好友」，各挂自己的单向属性。
> 大厂为什么选两条：① 好友属性几乎全是单向的（备注/分组/拉黑），一条存不下两人各自的属性；② 查「我的好友」是超高频操作，两条记录只需 `WHERE owner_id=我`（走索引、极快），不用 `or_` 双向查。读多写少，冗余换查询简单，值。
>
> **本学习项目为什么反而先用 1 条**：① 一条记录能逼你学 `or_` 双向查询 + 「从记录提取对方」（第 5 项的烧脑点），两条记录会绕过这个难点；② 状态流转（pending/accepted）一条更清晰；③ 等做到备注/分组（阶段二）亲身撞到「单向属性存不下」的墙，再理解为什么大厂用两条——**先用简单方案撞痛点、再懂复杂方案的为什么**，比死记结论学得深。到时可重构成两条记录，或单向属性单独建表。

### 难题 B：双向关系 + 单向属性的矛盾

- **好友关系是双向的**：A、B 是不是好友，对两人是同一个事实。
- **但有些属性是单向的**：备注（我叫你「老王」，你叫我「老张」）、拉黑（我拉黑你，你不知道）、分组（我把你分到「同事」，与你无关）。

矛盾：1 条记录存不下两个人各自的单向属性。解法思路（到时候选）：

- 单向属性单独存：另建表（如 `friend_remark` 表，存 `owner_id + friend_id + remark`），与 friendship 关系表解耦。
- 或好友关系本身就用 2 条记录，每条挂自己的单向属性。

### 难题 C：方向性校验

- 防重复：A 加了 B，B 不能再发起加 A（否则两条记录表示同一段关系）。发起申请前要**双向查**有没有已存在的关系。
- 防自加：`user_id != friend_id`。

## 四、friendship 表设计要点（第 1 项）

字段大致：

- `id` 主键
- `user_id` 外键 → users.id（发起方）
- `friend_id` 外键 → users.id（接收方）—— **两个外键都指向 users（自引用）**
- `status` 枚举：`pending` / `accepted` / `rejected`（用 `Mapped[FriendStatus]`）
- `create_time` / `update_time`

约束：

- 联合唯一 `(user_id, friend_id)`，防同方向重复申请。
- 自引用外键写法：`ForeignKey("users.id")`，两个列都写。
- 状态 Enum 单独定义（参考 PostStatus，见 [[likes-feature]] 用枚举的方式）。

难点：自引用时若要加 relationship，需要指定 `foreign_keys`（两个外键 SQLAlchemy 分不清哪个对哪个）——但阶段一可以**先不加 relationship，只存外键 id**，简单。

## 五、各功能实现要点提示（不含代码，自己写时参考）

- **2 发起申请**：查文章存在那套思路 → 查目标用户存在 → 双向查是否已有关系 → 防自加 → 创建 pending。
- **3 同意/拒绝**：按申请 id 查 → 校验当前用户是 friend_id（接收方）才能操作，否则 403 → 改 status。
- **4 待处理列表**：`where(friend_id == 我, status == pending)`。
- **5 好友列表**：`where(or_(user_id == 我, friend_id == 我), status == accepted)` → 遍历结果，每条里「对方」是 user_id 和 friend_id 中不等于我的那个（列表推导/条件提取）。
- **6 删好友**：双向定位那条记录后删除。
- **7 拉黑**：单向，建议独立黑名单表或独立状态；拉黑后在「发起申请」「查看」等处加拦截。
- **8 备注**：单向属性，见难题 B，可能单独建表。
- **9 分组**：分组表（属于某用户）+ 好友归组；想清楚一个好友能否在多个组（一对多 or 多对多）。
- **10 动态流**：先查我的好友 id 列表 → `where(PostDB.author_id.in_(好友ids))` 查这些人的文章 → 排序分页 → 预加载作者。
